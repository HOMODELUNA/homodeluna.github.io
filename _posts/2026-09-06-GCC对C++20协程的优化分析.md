## 摘要

本文以 `src/main.cpp` 中基于 ucoro 的两个协程(`coro_compute_squre`、`do_calc`)为样本,对比 GCC 13.3
在 -O0 / -O2 / -O3 下生成的汇编,考察编译器对 C++20 协程(协程帧、`co_await` 挂起/恢复、状态机 actor)的优化。

主要结论:

- **-O0 → -O2 收益巨大**:汇编从 9625 行 / 5118 指令降到 2709 行 / 1350 指令。31 个 `ucoro::*` 协程协议
  函数(`await_ready/suspend/resume`、`initial/final_suspend`、`coroutine_handle` 访问器等)被全部内联;
  挂起/恢复的对称转移(symmetric transfer)从嵌套 `call *%rdx` 变为 **尾跳转 `jmp *%rax`**(交接时机器栈归零,
  长协程链不涨栈);ramp 中冗余的“急切 actor 调用”被删除;帧字段写合并并经 SSE 向量化;状态分发从
  线性比较链改为位测试/二分。
- **-O2 → -O3 对协程几乎零收益**:协程帧布局、actor 状态机、尾跳转 resume 逐字节一致;唯一变化是更高
  内联预算把外围样板(`coro_start` 模板、`~awaitable` 析构、`std::any::reset`)并入 `main`/`do_calc.actor`。
- **仍未被优化的关键开销**:协程帧的 **堆分配 `operator new(88/96)` 在 -O2/-O3 均未消除**(各 4 次调用)。
  GCC 不做 coroutine-inlining / frame-elision,`coro_compute_squre(i)` 始终作为独立函数 + 独立帧存在。

**实践启示**:对 ucoro 这类基于标准 coroutine 机制的库,协程优化在 **-O2 已饱和**;进一步提级到 -O3
只会多内联样板而不改善协程本体。要压掉每协程一次的 `new`,需自定义 promise 的 `operator new/delete`
(静态分配 / 对象池帧),而非依赖更高的优化等级。

## 被测源码

`src/main.cpp` 定义了两个协程,基于 `ucoro::awaitable`:

```cpp
ucoro::awaitable<int> coro_compute_squre(int value) {
    co_return (value * value);
}

ucoro::awaitable<void> do_calc() {
    for (int i = 1; i < 100; i++) {
        auto result = co_await coro_compute_squre(i);
        std::cout << i << "*" << i << "=" << result << std::endl;
    }
    co_return;
}

int main(int argc, char **argv) {
    std::cout << "hello world!" << std::endl;
    coro_start(do_calc());
    return 0;
}
```

GCC 的协程 lowering 把每个协程拆成三部分:

- `<entry>`:创建协程帧 + ramp(执行到首个挂起点前)
- `.Frame.actor`:resume/destroy 合并后的状态机,用帧内 u16 状态字段做 switch 分发
- `.Frame.destroy`:销毁帧

## 编译器对协程做的核心优化(带证据)

### 1. 协程协议函数全部内联 —— 消除"每个 await 步骤一次真调用"

-O0 下,一次 `co_await` 会真实 `call` 一整套协议函数:`initial_suspend` →
`suspend_always::await_ready` → `await_suspend` → `await_resume` → `await_transform` →
`final_awaitable::*`,以及 `coroutine_handle::from_address / address / 转换符`(它们只是搬一个指针)。

-O2 下这 31 个 `ucoro::*` 辅助函数被内联并从符号表里彻底消失,`await_ready()` 的布尔判断直接融进控制流,
指针搬运被寄存器传递取代。**这是协程开销下降的最大来源。**

### 2. 挂起/恢复的对称转移(symmetric transfer)变成尾跳转 `jmp *`

最关键的一条。`do_calc.actor` 恢复 continuation 时:

- **-O0**(约 282 行):`call coroutine_handle::address()` 再 `call *%rdx` —— **嵌套 call**,
  被恢复协程压在调用者栈帧之上,长协程链会撑爆机器栈。
- **-O2**(约 278 行):先 `popq %rbx/%rbp/%r12/%r13/%r14; addq $32,%rsp` 把自己的栈帧完全退掉,
  再 `jmp *%rax` —— **尾跳转**。控制流交接时机器栈归零,协程链不再累积栈深度。

### 3. ramp 上的"急切 actor 调用"被删除(入口函数瘦身)

-O0 的 `<entry>`(`do_calcv` / `coro_compute_squrei`)分配帧后 `call ...Frame.actor` 跑一遍
initial-suspend 才返回。-O2 证明 initial_suspend 是 `suspend_always`(执行后立即挂起、只是往帧里写状态再返回),
于是把那次调用的效果直接折成入口里的几条 store,省掉一次完整的 actor 往返。
入口从 86 条指令缩到 20~28 条。

```asm
# -O2 do_calcv(entry):分配 96 字节帧后直接返回,不再 call actor
movl   $96, %edi
call   _Znwm@PLT
leaq   ...Frame.destroy(%rip), %rdx
leaq   ...Frame.actor(%rip),  %rcx
movq   %rcx, %xmm0
movq   %rdx, %xmm1
movq   %rax, (%rbx)
punpcklqdq %xmm1, %xmm0
movq   %rax, 48(%rax)
movups %xmm0, (%rax)          # 两个函数指针一次 16 字节写
movl   $65538, 56(%rax)       # resume点=2 与 帧已构造标志 合并成一条写
movups %xmm0, 16(%rax)        # 批量清零
ret                           # 无 eager actor call
```

### 4. 帧字段写入合并 + 向量化(SLP / store merging)

- -O0:actor 指针、destroy 指针、resume-state、构造标志位各用独立 `movq/movb/w` 一条条码进帧。
- -O2:`movq %rcx,%xmm0; movq %rdx,%xmm1; punpcklqdq %xmm1,%xmm0; movups %xmm0,(%rax)`
  —— 两个函数指针合并成一次 16 字节 SSE 写;`movl $65538, 56(%rax)` 把"resume点=2"和"帧已构造"
  标志位塞进同一条 32 位写;promise 区域用两条 `movups %xmm0` 批量清零。

### 5. 状态机分发从线性比较链 → 位测试/二分

-O0:`cmpl $7 / $5 / $1 / $3 / $6...` 一长串比较的 switch。
-O2 用 `cmpw/andl $-3` 二分;`coro_compute_squre.actor` 里甚至用
`movl $42,%edx; btq %rax,%rdx; jnc` —— 一条位测试(掩码 42 = 0b101010)判定合法状态,省掉多次分支。

### 6. 帧局部变量驻留寄存器、删除冗余重载;冷路径分离

-O0 把帧指针本身存在 `-40(%rbp)`,每一步 `movq -40(%rbp),%rax` 再解引用(单 actor 内 60 处 rbp 栈槽访问)。
-O2 把帧指针钉在 `%rbx/%rdi`,同类访问降到 11 处。
异常清理 / `bad_variant_access` / `rethrow` 等分支被移进 `.text.unlikely` 并生成 `.cold` 分身,
让热路径指令 cache 更紧凑。

## 编译器**没有**优化的部分(值得注意)

- **协程帧堆分配没被消除**:-O2 里 `do_calc`、`coro_compute_squre` 仍各自
  `call _Znwm@PLT`(`operator new(96)` / `new(88)`)。`coro_compute_squre(i)`
  **没有被协程内联(coroutine inlining / halo elision)进 `do_calc`** —— 它仍是独立函数、独立堆帧。
  GCC 目前没有实现"无挂起点协程的帧消除",这是本例最大的剩余开销。
- `operator delete` 计数从 11→0 并非泄漏被修掉,而是销毁路径变成了尾跳转
  `jmp _ZdlPv@PLT`,不再计入 `call`。
- 真正跨翻译单元/带虚调用的 `std::cout <<` 与 `std::any`(返回结果的 variant 提取)无法完全内联,
  `__ostream_insert / put / flush / bad_variant_access / _M_release` 等仍以实调用形式保留。

## 一句话结论(O0 → O2)

-O2 对协程的收益主要来自 **协程协议函数内联**、**对称转移改尾跳转(不涨栈)**、
**ramp 急切调用消除**、**帧字段写合并/向量化**与**冷路径分离**;而 **帧堆分配本身并未被消除**
(GCC 不做无挂起协程的 frame elision / coroutine inlining),所以本例每个协程仍有一次 `new`。
要压掉这次分配,需改用静态/池化 promise 的 `operator new/delete`,或换用支持 coroutine-inlining 的编译器路径。

## 追加:main-O3.S 相比 -O2 的进一步优化

## 结论先行

**-O3 对协程机制本身没有任何进一步优化。** 协程帧布局、actor 状态机、尾跳转 resume、
SSE 合并写帧在 -O2 与 -O3 之间逐字节一致。-O3 的全部收益来自 **更高的内联预算**,
把外围样板(模板 `coro_start`、`~awaitable` 析构、`std::any::reset`)并入调用方。

## 规模与关键指标对比

| 指标 | -O2 | -O3 |
| --- | --- | --- |
| 有效指令数 | 1350 | 1436(反而变多) |
| `coro_compute` entry | 28 insns / 1 call / 0 尾跳 | **完全相同** |
| `coro_compute` actor | 159 insns / 1 尾跳 | **完全相同** |
| `do_calc` entry | 20 insns | **完全相同** |
| `do_calc` actor | 355 insns | 369(+14,吸收了被内联的 cout/any 代码) |
| 堆分配 `operator new(96/88)` | 4 | **仍是 4(未消除)** |
| 对称转移尾跳转 `jmp *` | 4 | **仍是 4(不变)** |
| `ret` / `endbr64` 条数 | 26 / 43 | 19 / 41(函数边界减少) |

## -O3 相对 -O2 的唯一真实变化:更激进的内联

被彻底内联消失的辅助函数(定义数 / 调用数,O2 → O3):

| 符号 | O2 | O3 |
| --- | --- | --- |
| `coro_start<awaitable<void>>` | 1 def / 1 call | **0 / 0(全内联进 main)** |
| `awaitable<void>::~awaitable()` | 6 calls | **0(内联后塌缩为空)** |
| `std::any::reset()` | 1 def / 3 calls | **0 / 0** |
| `awaitable<int>::~awaitable()` | 2 calls | **0(在 do_calc.actor 内联)** |

`main` 里的体现:

- **-O2**:`call _Z10coro_startIN5ucoro9awaitableIvEEEDaOT_` + 3 处 `call awaitable<void>::~awaitable()`。
- **-O3**:`coro_start` 整个函数体(含它内部创建的第三个协程 `detach()::{lambda}` 及其 `new(96)`)
  直接铺进 `main`,变成内联的 `call awaitable<void>::detach(std::any)` + 若干 `call *%rax`
  (驱动协程 actor 的 resume),析构内联后被判定为空操作并删除。

## 为什么 -O3 对协程几乎零收益

1. **-O3 = -O2 + 少量额外 pass**(更激进函数内联、循环展开、`-fira-algorithm=priority` 等)。
   协程 lowering 阶段本身没有 O2/O3 分档——帧生成、actor 拆分、对称转移尾跳转在 -O1 之后即一致。
2. 循环 `for(i=1;i<100)` **横跨 `co_await` 挂起点**,位于 actor 状态机内部、每恢复一次只走一段,
   无法被 -O3 的循环展开器识别展开。
3. **帧堆分配 `operator new` 不被 -O3(也不被 -O2)消除**——GCC 无 coroutine-inlining /
   frame-elision(无挂起协程的帧内联/消除)。

## 一句话结论(O2 → O3)

`-O3` 相比 `-O2` 没有引入任何 **协程专属** 的优化,只是把剩余的外围样板按更高内联预算并入
`main` / `do_calc.actor`,从而减少函数边界、塌缩空析构;协程帧分配、actor 状态机与尾跳转 resume
完全不变。**对 ucoro 这类库,协程优化在 `-O2` 已饱和;真正的剩余开销(每协程一次 `new`)
只能靠自定义 promise 的 `operator new/delete`(静态/池化帧)解决,而非提高优化等级。**
